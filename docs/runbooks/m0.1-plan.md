# M0.1 Implementation Plan

Planning and verification document for the local M0.1 boundary. The first migration has now been written and runtime-verified under PocketBase v0.36.9. Sections 2 and 4 remain the reference for the accepted schema and the first component specs.

When approved, implementation proceeds in the order: local setup → migration write → migration run → seed spec review → seed fixture JSON → frontend init → atoms → ItemCard → MasonryGrid.

---

## Approved migration decisions

These four items surfaced during planning and were approved before `pocketbase/pb_migrations/0001_initial_schema.js` was written.

**F-1. Rights columns included.** The accepted migration includes `items.rights_status`, `items.rights_note`, and `items.rights_reviewed_at`. `SCHEMA.md` is updated to mirror this.

**F-2. Symmetric relationship ordering enforced by trigger.** SQLite CHECK constraints cannot reference `relationship_types`, so the accepted migration uses `trg_relationships_symmetric_ordering`, a `BEFORE INSERT` trigger that aborts unordered symmetric rows.

**F-3. `embeddings` scaffold included.** The accepted migration creates `embeddings` with `vector BLOB NOT NULL` as a placeholder. The table is empty in v0.1 and v1; vector query/storage details remain a v1.5 decision.

**F-4. FTS5 table uses explicit sync triggers.** The accepted migration creates `items_fts` with `content=''`, stores title, description, and summary, and keeps it in sync with `items` via insert/update/delete triggers keyed by SQLite integer `rowid`.

## 1. Local development setup

### 1.1 PocketBase binary

Download the latest stable release from `https://github.com/pocketbase/pocketbase/releases`. The minimum acceptable version is v0.22.0. The binary must match the host architecture (darwin_amd64 for Intel Mac, darwin_arm64 for Apple Silicon). Check the releases page for the current latest v0.x stable before downloading.

Runtime verification on 2026-04-29 used PocketBase v0.36.9 for macOS ARM64.

Place the binary at `pocketbase/pocketbase`. This path is already in `.gitignore`. Do not commit the binary.

Verify installation:
```
./pocketbase --version
```

### 1.2 Directory structure

The `pocketbase/pb_migrations/` and `pocketbase/pb_hooks/` directories already exist with `.gitkeep` placeholders. The runtime database and files directory (`pocketbase/pb_data/`) is created by PocketBase on first run and is already in `.gitignore`.

### 1.3 First run and admin user creation

Start PocketBase in development mode:
```
./pocketbase serve --dev
```

On first run, PocketBase creates `pb_data/` and opens the admin UI setup screen at `http://127.0.0.1:8090/_/`. Navigate there and create the admin (Owner) account with a strong password. Note the credentials in `.env` under `PB_ADMIN_EMAIL` and `PB_ADMIN_PASSWORD` (`.env` is gitignored).

Alternative: create the admin user from the CLI in newer PocketBase versions:
```
./pocketbase superuser create <email> <password>
```

Confirm the admin UI is accessible and the admin account works before running the migration.

### 1.4 Foreign key enforcement

SQLite does not enforce foreign keys by default. PocketBase v0.22+ enables FK enforcement automatically on its internal connections. Runtime verification under PocketBase v0.36.9 returned `PRAGMA foreign_keys = 1`, so no migration or hook change is needed for M0.1.

Action: after the migration runs, execute `PRAGMA foreign_key_list(relationships)` and confirm the FKs on `from_id` and `to_id` are active.

### 1.5 JS migration approach

PocketBase discovers and runs migration files in `pocketbase/pb_migrations/` on startup, sorted lexicographically by filename. In the current JS migration runtime, callbacks receive a transactional app instance:

```
/// <reference path="../pb_data/types.d.ts" />
migrate((app) => {
  // up — DDL statements executed via app.db().newQuery("SQL").execute()
}, (app) => {
  // down — reverse DDL
})
```

Use `app.db().newQuery("SQL").execute()` for each DDL statement. PocketBase runs migration callbacks transactionally. The accepted migration includes a small compatibility wrapper so it works with both the current app callback and the older direct-db callback shape.

Migration filename: `0001_initial_schema.js`.

Lexicographic sort of `0001_` is correct: it will always run before any `0002_` migration. Do not use a unix timestamp prefix for hand-written migrations — the sequential numeric prefix is more readable and unambiguous.

PocketBase tracks which migrations have run in its internal `_migrations` table. After the migration runs, verify with:
```sql
SELECT * FROM _migrations;
```

### 1.6 Development iteration

For schema corrections during v0.1 development (before production data exists), the acceptable approach is:
1. Delete `pocketbase/pb_data/` entirely
2. Fix the migration file
3. Re-run PocketBase (it re-creates `pb_data/` and re-runs all migrations)
4. Re-seed

This is only acceptable before production data exists (i.e., before v0.1 is in daily use). Once the Owner begins using the archive with real data, corrections go through a new numbered migration file — never by editing `0001_initial_schema.js`.

## 2. First migration content

This section is the accepted first migration content. Every table, column, constraint, index, and trigger is listed in plain text and mirrored by `pocketbase/pb_migrations/0001_initial_schema.js`.

Tables are listed in dependency order: tables referenced by foreign keys appear before the tables that reference them.

### 2.1 Notation

- `TEXT NOT NULL` — required string, stored as ISO 8601 UTC for timestamps
- `TEXT` (no NOT NULL) — nullable string
- `INTEGER NOT NULL` — required integer
- `REAL` — nullable float
- `BLOB` — binary data
- `DEFAULT value` — the column's default if omitted on insert
- `FK → table(column)` — foreign key constraint
- `CHECK(...)` — inline check constraint
- `UNQ(col1, col2)` — unique constraint on those columns
- `IDX(col1, col2)` — non-unique index on those columns
- `PARTIAL UNQ(cols) WHERE cond` — partial unique index

### Table: `relationships`

Purpose: one row per graph edge. Symmetric types use canonical ordering enforced by trigger (see F-2 above).

| Column | Type | Notes |
|---|---|---|
| id | TEXT NOT NULL | Primary key. |
| workspace_id | TEXT NOT NULL | FK → workspaces(id). |
| from_id | TEXT NOT NULL | FK → items(id). |
| to_id | TEXT NOT NULL | FK → items(id). |
| type | TEXT NOT NULL | FK → relationship_types(type). |
| weight | REAL | Nullable. CHECK(weight IS NULL OR (weight >= 0 AND weight <= 1)). |
| metadata | TEXT | Nullable. JSON, shape is type-specific. For `used_in`: `{"role": "primary" \| "supporting" \| "reference" \| "retired_from"}`. |
| note | TEXT | Nullable. Human-readable annotation on the connection. |
| asserted_by | TEXT NOT NULL | CHECK(asserted_by IN ('human', 'subagent:enrichment', 'subagent:import')). |
| created_at | TEXT NOT NULL | ISO 8601 UTC. |

Check constraints:
- `CHECK(from_id != to_id)` — self-relationships are forbidden.

Unique constraints:
- `UNQ(workspace_id, from_id, to_id, type)` — one row per directed edge per type per workspace.

Trigger (BEFORE INSERT, named `trg_relationships_symmetric_ordering`):
- When `NEW.type` corresponds to a row in `relationship_types` where `is_symmetric = 1`, and `NEW.from_id > NEW.to_id`, abort the insert with error "symmetric relationships must use canonical ordering: from_id < to_id".
- This trigger body requires a subquery on `relationship_types`. PocketBase's JS migration `db.newQuery(sql).execute()` supports multi-statement DDL; the trigger is a separate `CREATE TRIGGER` statement.

Indexes:
- `IDX(workspace_id, from_id, type)` — outbound relationship queries
- `IDX(workspace_id, to_id, type)` — inbound (reverse-direction) relationship queries
- `IDX(workspace_id, type)` — relationship type filters in graph view

### Virtual table: `items_fts` (FTS5)

Purpose: full-text search over canonical title, description, and summary fields. These are the only canonical text fields that feed search.

Structure: FTS5 external content table (content='' means no automatic content sync; explicit triggers maintain the index). Tokenizer: `porter ascii`.

Indexed columns (in order): `title`, `description`, `summary`. The FTS rowid corresponds to the SQLite internal integer rowid of the `items` table row.

Three triggers required:

1. `trg_items_fts_after_insert` — AFTER INSERT ON items. Inserts a row into `items_fts` with the new item's rowid, title, description, summary.

2. `trg_items_fts_after_update` — AFTER UPDATE ON items. When title, description, or summary changes: deletes the old FTS row by rowid, inserts the new one.

3. `trg_items_fts_before_delete` — BEFORE DELETE ON items. Removes the FTS row by rowid before the items row is deleted.

These triggers ensure the FTS index stays in sync with canonical fields. Only title, description, and summary are indexed; type, status, source, and tags are retrieved via structured filters, not FTS.

### 2.2 Transaction boundary

PocketBase runs migration callbacks transactionally. All `CREATE TABLE`, `CREATE INDEX`, `CREATE VIRTUAL TABLE`, and `CREATE TRIGGER` statements above are executed inside the single `migrate()` up callback. If any statement fails, PocketBase rolls the migration back and no partial schema exists.

### 2.3 Migration down function

The down function drops all tables and indexes in reverse dependency order. It is included for completeness but is never run in production once real data exists. For v0.1 development iteration, wiping `pb_data/` is faster and safer.

## 4. First three components in build order

The build order is: signal-row atoms → ItemCard → MasonryGrid. No component is written before the component it depends on. No component is written before the migration has been run and the seed data is loaded — the components are developed against real seeded data, not dummy props.

The frontend is not initialized in M0.1. These specifications are locked now so that when the Vite + React skeleton is initialized (the first step of M1), the atom and card specs are already frozen.

---

### 4.1 TypeIndicator (atom)

**Purpose:** Renders the type signal in the card's signal row. One of five fixed glyphs.

**File location (when written):** `src/components/atoms/TypeIndicator.tsx`

**Props:**
- `type: 'image' | 'caption' | 'note' | 'link' | 'campaign'` — required

**Rendered output:**

| type | glyph |
|---|---|
| image | `i` |
| caption | `c` |
| note | `n` |
| link | `l` |
| campaign | `ç` |

The glyph is rendered as a `<span>` in a monospaced typeface. No icon, no SVG. The ç for campaign is a visual convention — a letter that echoes "c" for campaign without colliding with "c" for caption.

**Typography:** inherits from the signal row container. The atom sets no font-size of its own — all sizing lives in the signal row's CSS.

**Color:** inherits from the signal row container. The atom sets no color. The signal row applies the muted color treatment when status is `retired`.

**Accessibility:**
- `aria-label="image item"` (or whichever type). The label is "{type} item" in lowercase.
- `role="img"` on the span (the glyph is a symbol representing the type, not a letter in a word).

**Forbidden:**
- No icon set (heroicons, lucide, etc.) — the glyph is the component.
- No color-coding per type. Type is indicated by shape (the glyph), not color.
- No tooltip on the glyph.

**No event handlers.** Purely presentational.

### 4.2 StatusIndicator (atom)

**Purpose:** Renders the status signal in the card's signal row. Short text label with sparse color treatment.

**File location (when written):** `src/components/atoms/StatusIndicator.tsx`

**Props:**
- `status: 'inbox' | 'triaged' | 'active' | 'archived' | 'retired'` — required

**Rendered output:** lowercase text label equal to the status value. No abbreviation.

**Color treatment:** the atom has two CSS classes: a base class (neutral grey, inherits from signal row) and a `retired` modifier (muted, ~60% opacity). Only `retired` receives a distinct treatment. The other four statuses render identically in neutral color. Color is via CSS class, not inline style.

**Typography:** same as TypeIndicator — inherits from signal row container.

**Accessibility:**
- `aria-label="status: {status}"` — e.g. `status: retired`.
- `role="status"` is not appropriate here (that has a live-region semantic); use no explicit role, letting it be a plain inline element.

**Forbidden:**
- No badge, no pill, no dot with a nested label. Just the text.
- No per-status color beyond retired-is-muted.
- No animation on status change (this atom re-renders; transitions are the parent's responsibility if needed).

### 4.3 SourceMark (atom)

**Purpose:** Renders the source signal in the card's signal row. Short lowercase monospaced mark identifying the capture origin.

**File location (when written):** `src/components/atoms/SourceMark.tsx`

**Props:**
- `source: string` — required. The source kind string from the database.

**Rendered output:** the `source` prop value, lowercased, in a monospaced typeface. Not a badge — a plain `<span>` with monospace font.

**Truncation:** do not truncate. Per `docs/component-rules.md`: "never abbreviated past recognizability." If a source kind string is unexpectedly long (a bug in the data), overflow is handled by the signal row's container, not by the atom.

**Recognized values in v1:** `pinterest`, `arena`, `url`, `manual`, `ios`. The component renders whatever string it receives; it does not validate or transform.

**Typography:** monospace typeface (the system monospace stack or a configured code font). Font-size inherits from the signal row.

**Color:** inherits. No per-source color coding.

**Accessibility:** `aria-label="source: {source}"`.

**Forbidden:** no icons, no logos, no brand colors per source (no Pinterest red, no Are.na blue). The mark is text, not branding.

### 4.4 UsageBadge (atom)

**Purpose:** Renders the optional usage signal in the card's signal row. Shows "used N×" when the item has been attached to campaigns. Hidden when count is zero.

**File location (when written):** `src/components/atoms/UsageBadge.tsx`

**Props:**
- `count: number` — required

**Rendered output:**
- When `count === 0`: render nothing. The component returns `null`. It takes up no space.
- When `count > 0`: render the text `used {count}×` where `×` is the multiplication sign character (U+00D7), not the letter x.

**Typography:** inherits from signal row.

**Color:** inherits. No special color for high count (e.g., no red at count > 5 — that would be an analytics-style visual judgment this product does not make).

**Accessibility:**
- When count > 0: `aria-label="used {count} times"`.
- When count === 0: null, no accessibility tree entry.

**Forbidden:**
- Never render "used 0×". Zero-count is the absence of the badge, not a visible zero.
- No color gradient from neutral to warning as count rises.
- No tooltip.

### 4.5 ItemCard

**Purpose:** The most-rendered component in the product. Renders a single item in the masonry grid with a mandatory four-signal row. Every instance must satisfy the contract in `docs/component-rules.md` "Card anatomy rules."

**File location (when written):** `src/components/items/ItemCard.tsx`

**Props:**

| Prop | Type | Required | Notes |
|---|---|---|---|
| id | string | yes | Item ID, used to navigate to /items/:id on click |
| type | 'image' \| 'caption' \| 'note' \| 'link' \| 'campaign' | yes | |
| status | 'inbox' \| 'triaged' \| 'active' \| 'archived' \| 'retired' | yes | |
| source | string | yes | Source kind string, passed to SourceMark |
| usageCount | number | yes | Passed to UsageBadge. 0 hides the badge. |
| imageUrl | string \| null | no | For type='image'. Null if not yet available. |
| captionText | string \| null | no | For type='caption'. The caption body. |
| noteParagraph | string \| null | no | For type='note'. First paragraph of the note. |
| ogImageUrl | string \| null | no | For type='link'. OG preview image. |
| ogTitle | string \| null | no | For type='link'. OG title, rendered below the image. |
| campaignCoverUrl | string \| null | no | For type='campaign'. |
| hasPendingAIAnnotations | boolean | no | Default false. When true, renders the pending-AI indicator. |
| rightsStatus | string \| null | no | When 'restricted' or 'expired', renders a quiet rights warning mark on the signal row adjacent to the status. |
| isSelected | boolean | no | Default false. Multi-select state — single-pixel accent border. |

**Layout (flex column, full height):**

1. **Content area** (flex-grow: 1): full-bleed rendering of the item's content.
   - `image`: `<img>` at full card width, height proportional. When `imageUrl` is null, renders a neutral static placeholder rectangle (no shimmer, no spinner).
   - `caption`: typeset text block. Body text in a slightly larger size than the signal row. Clamped at 6 lines with CSS line-clamp. No scroll. When `captionText` is null, static placeholder.
   - `note`: first paragraph in editorial type. Clamped at 4 lines. When `noteParagraph` is null, static placeholder.
   - `link`: OG image at top (or static placeholder), OG title below in a small text row. When both are null, renders the URL domain as text-only.
   - `campaign`: cover image (or static placeholder if no cover). Campaign title rendered on the cover image as an overlay strip at the bottom — dark background, white text. This overlay uses the `title` prop if available; omitted if title is null.

2. **Pending-AI indicator** (optional): a 3px-wide vertical line on the left edge of the card, visible only when `hasPendingAIAnnotations` is true. The color is a distinct informational tone (defined in the design token set, not hardcoded). Not in the signal row. Mutually exclusive with a signal-row `ai · pending` text mark — only one form of the indicator is used; the left-edge bar is preferred.

3. **Signal row** (flex row, single line, always visible):
   ```
   [TypeIndicator] · [StatusIndicator] [rights mark?] · [SourceMark] · [UsageBadge?]
   ```
   - Separator: `·` (middle dot, U+00B7) between TypeIndicator, StatusIndicator cluster, and SourceMark.
   - Rights mark: when `rightsStatus` is `'restricted'` or `'expired'`, a small `!` or `⚠` character rendered in a muted accent immediately after StatusIndicator and before the separator. No tooltip. Accessible via `aria-label` on the mark itself: `"rights: restricted"` or `"rights: expired"`.
   - UsageBadge appears at the end if count > 0; no separator before it (the badge's own space handles visual separation).
   - Padding: 6px vertical, 8px horizontal.
   - Font: 11–12px. Neutral grey. Not bold.

**Hover state:** a single-pixel border in the structural accent CSS variable (`--color-accent`). No shadow. No transform. No scale. No background change.

**Selected state** (`isSelected=true`): same single-pixel border in `--color-accent`. No other visual difference. The selection state is communicated to screen readers via `aria-pressed="true"` on the card container.

**Retired state** (`status='retired'`): the signal row text is in `--color-text-muted` (60% opacity or equivalent CSS class). The content area is rendered at 70% opacity via a CSS class. This applies to the entire card.

**Click behavior:** the entire card is a click target. Click navigates to `/items/{id}`. No part of the card has a secondary click target. Context-menu or long-press is handled by the grid, not the card.

**Accessibility:**
- The card container is `<article role="article">` with `aria-label="{title if available, else type + ' item'}"`.
- The content image has `alt="{title if available, else empty string}"`.
- `tabIndex={0}` and `onKeyDown` handling: Enter or Space navigates to the item detail route (same as click).

**Forbidden (per `docs/component-rules.md`):**
- Drop shadows (`shadow-md`, `shadow-lg`, etc.)
- Corner radius > 4px (the card uses 0–2px)
- Action buttons anywhere on the card
- Tag chips on the card
- Description text on the card
- AI annotation previews on the card
- Hover-only metadata
- Both a left-edge bar AND a signal-row `ai · pending` mark simultaneously

**Imports:** TypeIndicator, StatusIndicator, SourceMark, UsageBadge from atoms. A navigation utility (React Router's `useNavigate` or `Link`) for click handling.

### 4.6 MasonryGrid

**Purpose:** Renders a responsive masonry grid of ItemCard components. The primary browsing surface for inbox, archive, collections, and campaign asset groups.

**File location (when written):** `src/components/items/MasonryGrid.tsx`

**Props:**

| Prop | Type | Required | Notes |
|---|---|---|---|
| items | ItemCardProps[] | yes | Array of props objects for ItemCard. Empty array triggers empty state. |
| density | 'comfortable' \| 'dense' \| 'editorial' | yes | Controls column count and gap. |
| emptyState | ReactNode | no | Rendered when items.length === 0. The grid does not own empty state copy — the parent injects it. |
| loading | boolean | no | Default false. When true, renders the loading placeholder grid. |
| className | string | no | Additional CSS class applied to the outer container. |

**Layout: CSS Columns masonry.**

Implementation: `column-count` and `column-gap` set via CSS class selected by the `density` prop. Each `ItemCard` is a block element with `break-inside: avoid`. The CSS Columns approach lays items top-to-bottom within each column, then fills the next column. This is not true left-to-right masonry but is acceptable for v0.1.

Decision point: if column-order layout creates a poor browsing experience during dogfooding (e.g., chronologically newest items appearing mid-column instead of top-left), evaluate `react-masonry-css` as a v1 upgrade. This decision is deferred to v1; do not introduce the dependency at v0.1 without a stop-and-ask.

**Column counts by density:**

| density | ≥1200px (desktop) | 768–1199px (tablet) | < 768px (mobile) |
|---|---|---|---|
| comfortable | 3–4 (CSS: `column-count: 3`) | 2 | 2 |
| dense | 5 (CSS: `column-count: 5`) | 3 | 2 |
| editorial | 2 (CSS: `column-count: 2`) | 2 | 1 |

Breakpoints are applied via CSS (min-width media queries), not JavaScript.

**Gap:**
- comfortable: `column-gap: 12px; row gap via margin-bottom: 12px`
- dense: `column-gap: 8px; margin-bottom: 8px`
- editorial: `column-gap: 24px; margin-bottom: 24px`

**Empty state:** when `items.length === 0` and `loading` is false, renders the `emptyState` prop at full width. If `emptyState` is not provided, renders nothing (the parent is responsible for the empty state). The grid does not hardcode any empty state copy.

**Loading state:** when `loading` is true, renders a static (non-animated) placeholder grid — a grid of neutral `<div>` boxes with the same column count as the real grid, each box the height of approximately two image cards (300px). No shimmer animation. No color pulse. A static rectangle is sufficient. When `loading` returns to false and `items` is populated, the placeholder is replaced by real cards.

**Density toggle persistence:** the `density` prop is controlled by the parent. The archive route persists the density preference via localStorage (key: `archive_density`). The grid itself has no persistence logic — it renders whatever density it receives.

**Virtualization:** none in v0.1. The fixture set has ≤40 items; DOM performance is not a concern. Flag: if the Owner adds enough items that scroll performance degrades (rough threshold: > 200 visible cards), evaluate `@tanstack/react-virtual` as a v1 enhancement.

**Drag-and-drop:** not implemented in v0.1. The grid is a read/navigate surface only in M0.1/M1. Item-to-collection drag will be added in M3.

**Accessibility:**
- The grid container is `<section aria-label="items grid">` or the parent-provided label.
- Each ItemCard in the grid is independently accessible (see ItemCard accessibility spec above).
- No `role="grid"` — this is not an ARIA grid (rows + cells). It is a list of articles.

**Imports:** ItemCard from items/ItemCard.

## 5. Implementation order within M0.1

Once this document is approved line by line:

1. **Write the migration file.** Complete: `pocketbase/pb_migrations/0001_initial_schema.js` contains all accepted tables, indexes, and triggers.
2. **Run the migration.** Complete for local verification: PocketBase v0.36.9 accepted the migration as-is against isolated temp data. Run again against the real local `pocketbase/pb_data/` when setting up the development instance.
3. **Review and approve the fixture spec** (i.e., this section 3 was the spec; the next stop is the actual fixture JSON files). The JSON is presented for review before `seed/fixtures/*.json` is written.
4. **Write the seed loader** (`seed/load.ts`) and run it. Confirm the fixture data is queryable via PocketBase admin.
5. **Frontend initialization** (out of scope for M0.1). This is the first step of M1.
6. **Write atom components** (TypeIndicator, StatusIndicator, SourceMark, UsageBadge) against the specs in §4.1–4.4.
7. **Write ItemCard** against the spec in §4.5.
8. **Write MasonryGrid** against the spec in §4.6.
9. **Build /inbox route** using MasonryGrid + ItemCard against the seed data.

M0.1 is complete when the Owner opens the app locally, sees the seeded inbox items rendered in a MasonryGrid, clicks a card, and is navigated to `/items/:id` (even if the item detail page is a stub at this point).
