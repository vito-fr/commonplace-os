# v1 Scope

The narrowest version of the archive that proves the core loop end-to-end. Single user, single workspace, visual research instrument with campaign memory underneath.

This document sequences what ships in v1, what is explicitly excluded, and the conditions under which v1 is considered done. It does not introduce architecture, schema, or features beyond what `CONSTITUTION.md`, `SCHEMA.md`, `PLANNING_AUDIT.md`, `UI_ARCHITECTURE.md`, `docs/component-rules.md`, `docs/decisions/`, and `docs/subagents/` already lock.

When this document conflicts with the locked planning documents, the planning documents win. v1 scope is a downstream commitment, not a re-litigation.

---

## 1. v1 product summary

A single-user, single-workspace tool for capturing images, captions, notes, links, and campaigns from external and manual sources; storing them with provenance; connecting them via a typed graph; tracking lifecycle from inbox to retirement; and supporting marketing/creative work as the load test.

The Owner can: capture content into a quarantined inbox, inspect items in detail with AI-suggested metadata clearly distinguished from canonical content, connect items via typed relationships and collections, retrieve via full-text and structured search, reuse by attaching to campaigns with roles and rights warnings, and retire with optional replacement linkage. Behind it: continuous backup with weekly verified restore, nightly hygiene reports, append-only event audit log, and AI enrichment that never writes canonical fields.

v1 is one Owner, one workspace, one Hetzner VPS, one R2 bucket, three subagents (`import`, `ai-enrichment`, `hygiene`), and a focused frontend that prioritizes desktop work over mobile parity.

## 2. v1 scope by surface

The surfaces below are the only ones built in v1. Each surface has a defined contract from `UI_ARCHITECTURE.md` or `docs/component-rules.md`.

### 2.1 Foundation (non-UI)

- PocketBase backend running on Hetzner VPS, behind Tailscale
- SQLite database with the schema specified in `SCHEMA.md` and the first migration
- Litestream replicating the database to Cloudflare R2 continuously
- File storage on VPS local disk, mirrored to R2
- Default `personal` workspace seeded
- Owner authenticated via PocketBase
- Ollama running locally on the VPS with `nomic-embed-text` (scaffolded for v1.5; perceptual hashes computed in v1)
- Seed data loader using the curated 20–40-item fixture set
- Banned phrase blocklist seeded from `docs/anti-slop/banned-phrases.md`

### 2.2 Capture surfaces

- **Manual capture (web app):** paste a URL, upload a file, type a note. Each capture creates an item in `status='inbox'` with `source_id` resolved to the appropriate source row.
- **URL paste:** the system fetches OG metadata, classifies content type, and creates either a `link`, `image`, or `note` item depending on the response. URL hash is the `source_external_id`.
- **File upload:** drag-and-drop and file picker. Image files create `image` items with thumbnails generated on upload. Non-image files create `link` items pointing to the local-storage file_ref.
- **Manual note creation:** typed note via BlockNote, creates a `note` item with source kind `manual`.

Pinterest API and Are.na API integrations are out of scope; the URL-paste path covers their content for v1.

### 2.3 Inbox triage

- Inbox view at `/inbox`: queue of inbox items in chronological order
- Triage UI per `docs/component-rules.md` "Inbox triage rules": split layout, keyboard navigation (J/K/T/A/R/Enter/S/X/Esc), pending-AI-annotation review inline, tag application, collection picker, campaign attachment picker with role
- Bulk triage mode: multi-select grid with batch tag, batch advance, batch retire
- Empty-inbox state: single editorial line, no gamification

### 2.4 Archive and search

- Archive view at `/archive`: masonry grid of active items, density toggle (comfortable / dense / editorial)
- Filter rail: type, status, tag (approved only by default), collection, campaign, source, date captured, "has pending AI annotations," "used in campaign in last 30 days"
- Smart filters: "tagged X but not used in N days," "in inbox >M days," "stale active," "overused," "orphaned"
- Search bar (cmd-K) with FTS5 full-text over canonical title, description, and summary; tag search uses structured filters
- Search results in masonry by default; toggle to compact list

### 2.5 Item detail

- Item detail at `/items/:id` — always a route, never a modal
- Layout per `docs/component-rules.md` "Item detail rules": hero, metadata stack, description / summary panels, tag rows (approved + pending), relationships list, collections, campaign attachments, AI annotations panel, event timeline
- Tag application with vocabulary autocomplete (approved tags only)
- AI annotations panel collapsible, default collapsed for non-inbox items
- Always-visible actions: advance status, retire, attach to campaign, attach to collection, export, copy ID
- Promotion of approved annotations to canonical via explicit `Promote to canonical X` button

### 2.6 Collections

- Collection index at `/collections`
- Collection detail at `/collections/:id` with header, members masonry grid, add affordance (paste URL, drag, search-and-add)
- Bulk actions: remove from collection, retire, attach to campaign

### 2.7 Campaigns

- Campaign index at `/campaigns`
- Campaign detail at `/campaigns/:id` per `docs/component-rules.md` "Campaign page rules": hero, brief panel (BlockNote), attached assets grouped by role (primary / supporting / reference / retired-from), KPI panel when phase is wrapping or post_mortem, relationships panel, event timeline
- Campaign creation as an item with `type='campaign'` and a `campaign_profiles` extension row
- Phase indicator (`planning` / `live` / `wrapping` / `post_mortem`) distinct from `items.status`
- Asset attachment with role selector
- Detachment moves asset to retired-from group when campaign is `phase='live'` or later
- Rights warning per `docs/component-rules.md` "Rights warning rendering": none / advisory / blocking states

### 2.8 Graph view

- Graph view at `/graph` with filter sidebar
- Default zoom limited to ≤30 nodes; system tells the user to filter when the result set exceeds the cap
- Edges typed and color-coded; symmetric edges solid, directional edges arrowed
- Force physics OFF by default
- Node sizing by event count
- Click node → side panel with item summary and `Open detail` link; graph stays visible
- Hover edge → tooltip with type, weight, note, asserted_by, "explain this connection" affordance
- No 3D, no particles, no decorative motion

### 2.9 Hygiene

- Hygiene digest at `/hygiene` with all 11 reports defined in `docs/subagents/hygiene.md`: `inbox_debt`, `stale_active`, `retired_without_replacement`, `retired_by_inconsistency`, `cross_source_duplicates`, `tag_vocabulary_drift`, `overused`, `orphaned`, `dangling_annotations`, `banned_phrase_audit`, `restore_test_status` (the last is added in v1; see "scaffolded for later" if it surfaces real complexity)
- Nightly run scheduled at 03:00 local time
- Digest summary visible on home view; full reports at `/hygiene`
- Outstanding flags persist until resolved

### 2.10 Settings

- `/settings/sources` — per-source settings table with `default_privacy_level` editable inline
- `/settings/banned-phrases` — anti-slop blocklist administration with add / remove / reason
- Settings tables follow `docs/component-rules.md` "Table view rules": table-as-tool, full row signal pattern, bulk action toolbar

### 2.11 AI enrichment

- `ai-enrichment` subagent runs:
  - After every import batch (operates on newly-imported inbox items)
  - On Owner demand for a specific item or batch
  - Nightly pass over inbox items not yet enriched
- Generates annotations for `field_name` namespaces: `tags`, `description`, `summary`, `visual_dna`, `ocr_text` (low priority for v1; OCR is best-effort), `color_palette`, `relationship_suggestion`
- Auto-approves on inbox items; pending on all other statuses
- Anti-slop filters loaded at run start: banned phrases, tag vocabulary lock, length caps (140 chars description, 280 chars summary)

### 2.12 Operational

- Daily Litestream backup verified by file presence in R2
- Weekly automated restore test using the canary-item mechanism documented in `PLANNING_AUDIT.md` §11
- Hygiene subagent reports surface in home view nightly
- Manual export of an item or campaign as JSON

### 2.13 What is NOT a v1 surface

The following routes and components are explicitly NOT in v1:

- Curator / nightly synthesis output
- Semantic search results page (the search bar exists, vector queries do not)
- Visual similarity browse view
- License expiry dashboard
- Multi-workspace switcher (the schema supports it; the UI does not surface it because count is always 1)
- Mobile triage beyond single-item flows
- Browser extension polish (URL-paste fallback covers this)
- iOS share-sheet polish (URL-paste fallback covers this)
- Public sharing or read-only views
- Approval queue separate from per-item triage (suggestions are reviewed in-context)
- Automated takedown or rights-expiry notification

## 3. v1 milestone sequence

Milestones are vertical slices. Each ends in a demoable state — a clear, observable outcome the Owner can verify before moving on. Milestones depend on prior ones; reordering breaks the dependency chain.

### M0 — Foundation

**Scope:**
- Initialize the repository with all governance documents already written
- Provision the Hetzner VPS, Tailscale, and Cloudflare R2 bucket
- Install PocketBase and run on the VPS behind Tailscale
- Write the first PocketBase JS migration `pocketbase/pb_migrations/0001_initial_schema.js` containing all tables, indexes, and triggers from `SCHEMA.md`
- Seed the default `personal` workspace, the Owner user, and the relationship type registry
- Implement the seed-data loader and load the curated fixture set
- Configure Litestream → R2 continuous replication
- Implement the canary-item harness for restore tests
- Manual restore-to-staging rehearsal once

**Dependencies:** none.

**Demoable end state:** Owner runs `pnpm dev` (or equivalent) locally, points at the staging PocketBase, sees the seeded fixtures via PocketBase admin. Triggers a manual restore-to-staging from R2 and verifies the canary item is queryable end-to-end. Litestream lag is sub-second.

### M1 — Capture

**Scope:**
- Frontend skeleton: Vite + React + routing
- `ItemCard` with the four-signal row (this component ships before any other UI)
- Inbox view at `/inbox` rendering inbox items as a masonry grid
- Manual capture surface: paste URL, upload file, type note
- URL-paste flow: OG metadata fetch, content classification, item creation
- File-upload flow with thumbnail generation
- `import` subagent activated for the URL-paste and file-upload paths
- `imported` events logged
- Source rows auto-created for new sources
- Idempotent identity check on re-paste of an existing URL

**Dependencies:** M0.

**Demoable end state:** Owner opens the app, pastes a URL into the capture bar, sees a card appear in inbox with type / status=inbox / source=`url` / no usage. Re-pastes the same URL; sees `update_count` increment without duplicate. Uploads a local image file; sees a card with type=`image`, thumbnail rendered.

### M2 — Inspect

**Scope:**
- Item detail route at `/items/:id`
- Hero rendering for all five item types
- Metadata stack with title editing, status display, source link, timestamps, privacy chip, rights chip
- Description / summary panels (canonical, human-only)
- Tag row (approved tags) with vocabulary autocomplete
- AI annotations panel (collapsible) rendering pending annotations with `ProvenanceMark`
- Triage UI per component rules: split layout, keyboard navigation, approve/reject AI suggestions inline
- `ai-enrichment` subagent activated: runs after every import batch and on demand; populates `ai_annotations` for inbox items with auto-approval, for non-inbox items with `pending`
- Banned phrase filter and length caps enforced
- `annotation_added`, `annotation_approved`, `annotation_rejected`, `tagged`, `untagged` events logged
- Status transition action: inbox → triaged → active

**Dependencies:** M1.

**Demoable end state:** Owner opens an inbox item, sees AI-suggested tags rendered with dashed outline and `pending` affix, sees AI-suggested description in a separate panel with model name and confidence visible. Approves a tag; it transitions to chip style. Promotes the AI description to canonical via the explicit button; description appears in the canonical panel. Advances item to `active`.

### M3 — Connect

**Scope:**
- Relationships table active with the eight initial types from `docs/relationships.md`
- Add-relationship affordance from item detail with type picker, target item search, optional note, weight
- Relationships list rendering on item detail with the full contract from `docs/component-rules.md` "Item detail rules"
- Backlinks visible (queries `to_id` index for inbound relationships)
- Collections: index page, detail page, add-to-collection from item detail, bulk actions
- `relationship_added`, `relationship_removed`, `collection_added`, `collection_removed` events logged
- Symmetric type trigger enforced (`from_id < to_id`)

**Dependencies:** M2.

**Demoable end state:** Owner opens item A, clicks "add relationship," types `inspired_by` and selects item B. Relationship renders on both A's outbound and B's inbound list. Adds A to a collection; opens the collection page; sees A in the members grid. Removes a relationship; sees it disappear and the corresponding event in both timelines.

### M4 — Retrieve

**Scope:**
- FTS5 virtual table populated and triggered on item insert / update
- Full-text search via cmd-K with results in masonry layout
- Filter dropdown: type, status, tag (approved), collection, campaign, source, date captured
- Smart filter rail with at least three saved filters: "Inbox debt >14 days," "Stale active >90 days," "Overused this quarter"
- Negative / temporal filters: "tagged X but not used in N days"
- Toggle to compact list view
- Search results respect workspace scoping

**Dependencies:** M3 (smart filters depend on event coverage from prior milestones).

**Demoable end state:** Owner runs a full-text search, sees masonry results. Adds a tag filter, sees results narrow. Opens "Stale active" smart filter, sees items that haven't moved in 90 days. Runs "tagged spring but not used in 60 days," sees the expected items.

### M5 — Reuse

**Scope:**
- Campaigns as items: creation flow, `campaign_profiles` extension populated
- Campaign index at `/campaigns`
- Campaign detail page per component rules: hero, brief panel (BlockNote), assets grouped by role, KPI panel rendered conditionally, relationships, event timeline
- Asset attachment via drag-and-drop or search-and-add, with role selector
- Phase changes (`planning` / `live` / `wrapping` / `post_mortem`) distinct from item status
- Rights chip on item detail
- `RightsWarning` component active at attachment with three states: none / advisory / blocking
- Override path on advisory: requires note, logs event with `metadata.rights_warning_state` and `metadata.override_note`
- Hard-block on `restricted` and `expired`: dialog offers status change or cancel
- `campaign_attached`, `campaign_detached` events logged
- Detachment from a `live`+ campaign moves asset to retired-from group

**Dependencies:** M4.

**Demoable end state:** Owner creates a campaign with `phase='planning'`, sets a brief, attaches three items at roles primary, supporting, reference. Advances to `phase='live'`. Tries to attach a `restricted` item; sees blocking dialog with no override. Attaches an `unknown` item; sees advisory warning, types a note, override succeeds. Detaches one item; it appears in the retired-from group, muted but visible.

### M6 — Retire

**Scope:**
- Status transitions: `active → archived → retired` with reverse paths
- Retire action with optional `replaced_by_item_id`; creates a `retired_by` relationship when set
- Retired items hidden from default archive view; opt-in toggle to surface them
- `status_changed`, `retired` events logged
- Restoration: `retired → active` allowed, logs `status_changed`

**Dependencies:** M5 (retired-from-campaign depends on campaign attachments).

**Demoable end state:** Owner retires item A with item B as the replacement. Item A vanishes from default archive view. Item B's detail shows the inbound `retired_by` relationship. The retired-from group on the campaign that used A still shows A muted. Owner toggles the archive view filter to "include retired"; sees A again.

### M7 — Graph

**Scope:**
- Graph view at `/graph` rendering active items and their relationships
- Filter sidebar: type, relationship type, status, collection, campaign, date range
- Default zoom enforced ≤30 nodes; "filter further" prompt when exceeded
- Typed color coding consistent across all graph views
- Symmetric edges (solid) vs. directional (arrow) rendering
- Static layout default; force toggle opt-in
- Node sizing by event count
- Click node → side panel; click edge → tooltip with full metadata
- "Explain this connection" affordance

**Dependencies:** M6 (graph rendering uses the full lifecycle).

**Demoable end state:** Owner opens graph filtered to one collection. Sees ≤30 nodes with typed edges color-coded. Clicks a node, side panel slides in with item summary and "open detail" link; graph stays visible. Hovers an edge, sees the relationship note and asserted_by mark.

### M8 — Hardening

**Scope:**
- `hygiene` subagent activated with all 11 reports
- Nightly cron at 03:00 local
- Hygiene digest on home view; full reports at `/hygiene`
- Weekly automated restore test with canary-item verification
- Restore test failure surfaces as a critical hygiene flag
- Source administration page at `/settings/sources`
- Banned phrases administration page at `/settings/banned-phrases`
- Item-level export (JSON) and campaign-level export (JSON with attached assets)
- `exported` events logged
- Manual deletion path with `deleted` event logged before row removal
- Empty states reviewed against the title-why-action contract

**Dependencies:** M7 (the hardening pass touches every surface to ensure compliance).

**Demoable end state:** Hygiene runs at 03:00, produces a digest with all 11 reports. Owner sees the home view summary the next morning. Restore test runs Sunday at 02:00, verifies canary, marks success. Owner opens `/settings/sources`, edits the default privacy of the Pinterest source, sees the change reflected on next paste. Exports a campaign as JSON; reviews the file structure.

## 5. v1 done criteria

v1 is shipped when ALL of the following are true.

### Core loop verbs (must demonstrate end-to-end)

1. **Capture:** Owner can paste a URL or upload a file and observe the item appear in inbox within 5 seconds, with source, status, and type signals correct.
2. **Inspect:** Owner can open any item's detail route, read all canonical fields, see AI annotations rendered with `ProvenanceMark`, view the event timeline.
3. **Triage:** Owner can approve / reject AI suggestions, apply tags, advance status, in keyboard-only flow.
4. **Connect:** Owner can create relationships of multiple types between items, add items to collections, see backlinks on item detail.
5. **Retrieve:** Full-text search returns expected results; tag, status, source, collection, campaign filters work; at least three smart filters work (`Inbox debt`, `Stale active`, `Overused this quarter`).
6. **Reuse:** Owner can attach an item to a campaign with a role; rights warning fires correctly across all three states (none / advisory / blocking); attached items appear under the correct role group.
7. **Retire:** Owner can retire an item with or without replacement; retired items hidden by default; the retired-from group on past campaigns retains them.

### Systemic requirements

8. **Workspace scoping:** every query against a tenant-scoped table is filtered by `workspace_id`. Verified by code review and by automated test coverage on the data-access layer.
9. **AI canonical isolation:** automated test verifies that no `ai-enrichment` subagent path can write to canonical fields under any input.
10. **Event coverage:** every event listed in the v1-required column of `PLANNING_AUDIT.md` §8 is logged at the documented action.
11. **Backup verification:** the weekly restore test has run successfully at least three consecutive weeks before v1 is declared shipped.
12. **Hygiene cadence:** nightly hygiene run produces all 11 reports; the digest is visible on home view.
13. **Component compliance:** zero forbidden component classes shipped; every `ItemCard` carries the four-signal row; every AI-rendered string carries a `ProvenanceMark`; item detail is always a route.
14. **Anti-slop filters:** verified that AI-generated output containing banned phrases triggers regeneration, not silent stripping.
15. **Seed data integrity:** loading the seed fixture set produces the documented coverage (all item types, multiple sources, multiple relationship types, multiple rights statuses, multiple AI annotation states, retired item with replacement).

### Documentation

16. `docs/runbooks/restore.md` exists and has been used to perform a manual restore at least once.
17. `docs/runbooks/environment.md` exists with the full `.env` variable list.
18. `docs/sessions/` is populated with end-of-session reports per the format in `CLAUDE.md`.

v1 is not done if any of the above fails. Partial completion is not v1.

## 6. Features scaffolded for later but not built in v1

Schema and registry slots exist now to avoid migration pain in v1.5+. The slots are populated by zero rows and exposed by zero UI in v1.

### Vector storage

- An `embeddings` table with `(item_id, field_name, model_name, model_version, vector)` exists in the schema; populated by zero rows in v1.
- The M0.1 schema uses `vector BLOB NOT NULL` placeholder storage; no query path consumes it in v1.
- Decision deferred per `PLANNING_AUDIT.md` §14: native sqlite-vec storage/query details are resolved when v1.5 vector queries are scoped.

### Perceptual hash

- `items_image.perceptual_hash` is computed on every image upload in v1 and used for the `cross_source_duplicates` hygiene report.
- The hash is NOT used to drive a visual search UI in v1; that is v1.5.

### Workspace identity

- `workspace_id` is enforced on every tenant-scoped table from M0.
- The schema supports more than one workspace; v1 UI only ever surfaces the default `personal` workspace.
- The workspace switcher component is not built; it appears in v1.5+ when count > 1.

### Workspace members

- `workspace_members(workspace_id, user_id, role)` is NOT scaffolded in the schema in v1. It is documented in `PLANNING_AUDIT.md` §7 only.
- Adding the table is a stop-and-ask in v1.5+ when multi-user is in scope.

### AI annotation field_name extensibility

- The `field_name` namespaces used in v1: `tags`, `description`, `summary`, `visual_dna`, `ocr_text`, `color_palette`, `relationship_suggestion`.
- Adding new namespaces is a stop-and-ask but requires zero schema migration.
- `semantic_neighbors` namespace is reserved but not populated in v1.

### Relationship type registry

- Eight initial types active in v1: `inspired_by`, `references`, `derived_from`, `annotates`, `used_in`, `retired_by`, `contradicts`, `visually_similar_to`.
- `precedes`, `follows`, `responds_to`, `cross_workspace_reference` are reserved in `docs/relationships.md` but not registered in the registry table in v1.

### Source kinds

- Source kinds active in v1: `manual`, `url`, plus `ios_capture` opportunistically if the user pastes from the iOS share-sheet (treated as a `url` source variant).
- `pinterest`, `arena`, `local` source kinds are described in the import subagent contract but the dedicated import paths for them are not built. URL-paste covers their content.

### Privacy levels

- `default_privacy_level` on `sources` and `privacy_level` on `items` are populated and resolution works.
- v1 enforces zero access control based on privacy levels — they are advisory metadata only. The advisory help text in settings makes this explicit.

### Restore test status reporting

- The `restore_test_status` hygiene report is the eleventh report in v1. Decision deferred during implementation per `PLANNING_AUDIT.md` §14.
- If real complexity surfaces (e.g., the report requires additional schema), the report ships in v1.5 instead and v1 ships with the 10 other reports from `docs/subagents/hygiene.md`.

## 7. First implementation order

The order in which the M0 milestone is executed. Subsequent milestones inherit dependencies from `SCHEMA.md` and the milestone definitions above; they do not require their own implementation order.

1. **Initialize the repository.** Commit all governance documents already produced — `CONSTITUTION.md`, `CLAUDE.md`, `SCHEMA.md`, `UI_ARCHITECTURE.md`, `PLANNING_AUDIT.md`, `docs/`, this scope document — as the first commit. No code yet.
2. **Provision infrastructure.** Hetzner VPS, Tailscale, Cloudflare R2 bucket with versioning + 30-day lifecycle.
3. **Install PocketBase.** Run as a single binary on the VPS. Confirm reachable via Tailscale only.
4. **Write `pocketbase/pb_migrations/0001_initial_schema.js`.** Contains every table from `SCHEMA.md` plus indexes, triggers, CHECK constraints, and FK constraints. This is a stop-and-ask before the file is written; the Owner reviews and approves.
5. **Run the migration on the VPS.** Verify all tables exist, CHECK constraints and triggers are active, and all indexes are present.
6. **Seed default workspace, Owner user, relationship type registry, banned phrase blocklist.** A one-shot loader writes seed data; migrations remain schema-only unless explicitly approved otherwise.
7. **Build the seed-data loader.** A small script that reads the curated fixture JSON and inserts rows. Includes the canary item.
8. **Configure Litestream.** Replicate to R2 continuously. Verify lag.
9. **Build the canary-item harness for restore tests.** A standalone script that restores a fresh database from R2 and runs the three checks (schema version match, canary queryable, canary file SHA-256 match).
10. **Run a manual restore-to-staging.** Verify end-to-end restore in under 60 minutes.
11. **Write `docs/runbooks/restore.md`** based on the manual rehearsal.
12. **Stand up the Vite + React skeleton.** Routing, basic layout, no components beyond the shell.
13. **Build `ItemCard` first.** This is the most-rendered component in the product; its four-signal-row contract is the design test that everything else is measured against. Build it, render it against the seed data, verify the contract.

After step 13, M1 begins.

## 8. v1 risks and stop conditions

Real risks identified during planning and implementation foresight. Each carries a stop condition that halts new work when triggered.

### Risk: schema mistakes locked in early

- **Vector:** The first migration is the riskiest moment in the project. A mistake here creates permanent migration debt.
- **Mitigation:** Stop-and-ask before `pocketbase/pb_migrations/0001_initial_schema.js` is written; the Owner reviews the migration line by line. Weekly restore test as ongoing canary.
- **Stop condition:** A schema migration produces unexpected behavior in production OR a column / constraint is found to be wrong after the migration runs. Halt all new work until the corrective migration is written, reviewed, and tested.

### Risk: backup never verified

- **Vector:** Litestream runs successfully every minute, but a backup that has never been restored is a dead backup.
- **Mitigation:** Weekly automated restore test from M0 onward, with canary-item verification.
- **Stop condition:** The restore test fails two weeks running. Halt all new work, fix backup before any other change.

### Risk: AI canonical isolation broken

- **Vector:** A subagent code path discovers it can write to a canonical field through some indirect API or a forgotten edge case. Trust in the system collapses on the day this happens.
- **Mitigation:** Automated test in the M2 milestone verifying no enrichment subagent path can write canonical. The ADR 0003 rule is enforced at the data-access layer, not just in subagent code.
- **Stop condition:** A canonical field is found to have been written by an AI subagent. Halt all new work, audit history, fix the subagent contract and the data layer, write an ADR.

### Risk: forbidden component class shipped

- **Vector:** Claude Code generates a component that matches the named-forbidden list (`KPICard`, `InsightCard`, etc.) under a different name, or applies forbidden visual patterns.
- **Mitigation:** `docs/component-rules.md` stop-and-ask triggers; design review at every milestone end-state.
- **Stop condition:** A forbidden component class or pattern is found in the shipped frontend. Revert, write an ADR, identify the gap in the rules that allowed it.

### Risk: capture friction kills usage

- **Vector:** The thing that makes archives die is friction at the capture step. If pasting a URL takes more than 5 seconds, the archive degrades.
- **Mitigation:** M1 acceptance includes a 5-second-from-paste-to-card check. Seed data covers diverse source types so the capture path is exercised broadly.
- **Stop condition:** Owner finds themselves not capturing because the flow is too slow or too noisy. Halt feature work, audit the capture path, simplify before continuing.

### Risk: rights warning UX gets in the way

- **Vector:** The rights warning fires too aggressively, interrupting fast attachment work. The user starts overriding without reading.
- **Mitigation:** Three-state design (none / advisory / blocking) — most attachments fire `none`. Override notes are required only for advisory states, not for everyday flows.
- **Stop condition:** Override-without-read pattern detected (advisory overrides clustered in time, notes are perfunctory). Halt and re-evaluate the warning thresholds.

### Risk: AI enrichment slop reaches approved tags before the queue is functional

- **Vector:** Inbox auto-approval is convenient; if the triage UI lags or the user skips review, AI tags accumulate unreviewed.
- **Mitigation:** Pending tags excluded from autocomplete and search until promoted. Hygiene flags `pending` tags older than 30 days. Banned phrase filter at run start.
- **Stop condition:** Approved tags found to contain banned phrases or generic AI slop. Halt enrichment subagent runs until the filter pipeline is audited.

### Risk: graph performance at the 30-node default

- **Vector:** Even at 30 nodes, the graph may render slowly or interactively poorly on mid-range hardware.
- **Mitigation:** M7 acceptance includes responsiveness checks. Force physics OFF by default reduces compute. Filter-first design forces small graphs.
- **Stop condition:** Graph interaction lag exceeds 100ms on Owner's primary device. Profile, optimize, or further reduce default zoom cap.

### Risk: scope creep mid-milestone

- **Vector:** "Just one more thing" within a milestone delays demoable end-state by days. Multiplied across 9 milestones, this kills v1.
- **Mitigation:** Done criteria for each milestone are concrete and verifiable. Stop-and-ask on bulk changes.
- **Stop condition:** A milestone exceeds its planned scope by more than 30% of effort. Pause, reduce scope, ship the demoable end-state, defer the rest to a later milestone or to v1.5.

### Risk: BlockNote complexity for caption and brief editing

- **Vector:** BlockNote's API surface is rich; using it correctly for captions (M1/M2) and campaign briefs (M5) may consume more time than anticipated.
- **Mitigation:** Use BlockNote at minimum capability in v1: plain markdown blocks, no custom block types, no plugins. Defer custom block work to v1.5.
- **Stop condition:** BlockNote integration consumes more than two days in any single milestone. Switch to a textarea fallback for that milestone and add BlockNote in a focused later pass.

### Risk: Litestream + R2 setup failures discovered late

- **Vector:** Backup configuration looks correct but fails silently under real load or specific WAL patterns.
- **Mitigation:** M0 includes a manual restore rehearsal. Weekly automated test from M0 onward.
- **Stop condition:** Litestream fails to replicate for any period longer than 30 minutes during normal operation. Halt all new work; this is the system's lifeline.

### Risk: search performance degrades with many tags

- **Vector:** FTS5 with hundreds of approved tags and many `item_tags` rows may slow queries.
- **Mitigation:** Indexes on `item_tags` per `SCHEMA.md`. Queries written to leverage them.
- **Stop condition:** Search response time exceeds 500ms on Owner's seeded dataset. Profile, add covering indexes, or rethink query patterns. Do not paper over with caching in v1.
