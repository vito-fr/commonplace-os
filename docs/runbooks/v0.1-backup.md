# v0.1 Manual Backup Runbook

v0.1 runs locally on the Owner's laptop. There is no Litestream, no Cloudflare R2, no automated restore test. Backup is the Owner's manual discipline.

This runbook is the complete procedure. It is short on purpose: the more steps a manual procedure has, the less it will be followed.

When v1 ships, this runbook is superseded by `docs/runbooks/restore.md` (production restore from R2).

---

## When to back up

- **Always before any schema migration.** Even when the migration is "obviously safe."
- **Always before re-running the seed loader** if the seeded archive contains real captures the Owner has accumulated.
- **Always before bulk operations** that affect more than 50 rows.
- **Weekly, regardless of activity.** A standing weekly backup catches the case where an unobserved problem has been accumulating.

The minimum cadence is weekly. The maximum gap between backup and restore drill is one month.

---

## What to back up

Two artifacts:

1. The PocketBase data directory: `pocketbase/pb_data/`
2. The seed fixtures: `seed/fixtures/`

The seed fixtures are also in git, so they're recoverable from git history. But backing them up alongside `pb_data/` keeps the snapshot self-consistent — if the loader version that wrote the data was a particular fixture set, the matching fixture files are recoverable from the same backup.

Source code, governance documents, and configuration files are in git. The git history is the source of truth for them. Backing them up is redundant and not part of this runbook.

---

## Where to back up

To an **external drive** that is not the laptop's primary storage. A USB SSD or an external HDD. Not iCloud, not Dropbox, not a sync folder. The point of the backup is that a primary-storage failure does not destroy it; sync services replicate the failure.

Create a backups directory on the external drive:

```
/Volumes/<drive>/archive-backups/
```

Inside, each backup is a timestamped directory:

```
/Volumes/<drive>/archive-backups/2026-04-28-1430/
```

`YYYY-MM-DD-HHMM` ensures lexicographic and chronological ordering match.

---

## How to back up

Stop PocketBase first. Backing up while PocketBase is writing to SQLite risks an inconsistent snapshot.

```bash
# 1. Stop PocketBase (Ctrl-C in its terminal, or kill the process)

# 2. Verify it's stopped — should return nothing
ps aux | grep pocketbase | grep -v grep

# 3. Create the timestamped backup directory
TIMESTAMP=$(date +%Y-%m-%d-%H%M)
BACKUP_DIR="/Volumes/<drive>/archive-backups/$TIMESTAMP"
mkdir -p "$BACKUP_DIR"

# 4. Copy pb_data and seed fixtures
cp -R pocketbase/pb_data "$BACKUP_DIR/pb_data"
cp -R seed/fixtures "$BACKUP_DIR/fixtures"

# 5. Record the git HEAD so the restore can be matched to the right code state
git rev-parse HEAD > "$BACKUP_DIR/git_head.txt"

# 6. Verify size — empty backups indicate a copy failure
du -sh "$BACKUP_DIR"

# 7. Restart PocketBase
./pocketbase/pocketbase serve
```

The whole procedure is under 60 seconds for a v0.1-sized archive.

## Restore drill

A backup that has never been restored is a dead backup. The Owner performs a restore drill at least once per month, more frequently if the archive contains content that would be painful to lose.

**Restore drill procedure:**

1. Pick a recent backup (not the most recent — that's the one you'd use in a real emergency; drill on something one or two backups old).
2. Create a fresh staging directory next to the repo: `archive-staging/`
3. Initialize an empty PocketBase data structure inside it.
4. Copy the backup's `pb_data` over the staging `pb_data`.
5. Check out the git revision recorded in `git_head.txt` into the staging repo.
6. Start PocketBase against the staging data dir.
7. Verify: log in as Owner, browse a few items, run a search, confirm at least one campaign opens with its attached assets.
8. Tear down the staging environment.

Total time should be under 15 minutes once the procedure is familiar.

If anything in the verification step fails: STOP. The backup mechanism is broken. Fix it before continuing v0.1 work. This is a stop condition.

---

## Retention

- Keep all weekly backups for the last 2 months
- Keep the first backup of each month indefinitely
- Prune older weekly backups quarterly

Storage cost is negligible at v0.1 scale. Erring toward more retention is correct.

## What this runbook does NOT cover

- Backing up the source code (in git, separate concern)
- Backing up the governance documents (in git, separate concern)
- Continuous backup (v1)
- Off-site backup (v1)
- Automated restore verification (v1)
- Point-in-time recovery (v1)

When v1 ships, all of the above are addressed by Litestream + R2 + the canary-item harness, and this runbook is superseded.
